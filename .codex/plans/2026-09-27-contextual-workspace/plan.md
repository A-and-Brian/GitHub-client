# Keep your place
UI review and implementation plan · 2026-09-27

## Decision proposed
Keep the existing application sidebar and organization/team/repository page shell. Each entity has its own header and section tabs. Its Pull requests tab contains the shared Inbox filtered to that entity, with the PR detail beside the list inside that same tab panel. Opening a PR never removes the entity header or section tabs. Keep existing landing behavior: organization/team Overview and repository Code remain the defaults; the global Inbox remains its own destination. Opening a check opens a dialog over that PR. Closing a detail restores the exact source position.

Revision 2 incorporates Yi’s feedback: the scoped Inbox is nested inside the organization/team/repository Pull requests tab. The parent header and sibling tabs stay visible with a PR open. The repository navigator/preview mockup was explicitly accepted ("This looks perfect") and is unchanged. The prior review decision was annotated, not approved.

## Current evidence
- apps/desktop/src/app/router.tsx: org, team, repo, inbox, PR, runs, and run detail are sibling routes. PR search stores only its tab; source context is absent.
- apps/desktop/src/screens/repository.tsx: repository PR links navigate to the standalone PR route. Code uses one contents result for either a directory or a file; README renders below the root directory only.
- apps/desktop/src/screens/pull/pull-page.tsx: PullContent is already reusable between Inbox and standalone PR. PullPage Back calls window.history.back(); keyboard shortcut 3 selects Checks.
- apps/desktop/src/styles.css: the current checks sidebar appears at a PR body width of 1152px. The header is outside that body container, so merely adding a CSS rule inside it cannot control the header tab correctly.
- apps/desktop/src/components/repository-context.tsx: Actions and Settings are in a separate small navigation strip. RepositoryBrowser also has its own Code/Pull requests controls.
- apps/desktop/src/screens/repository-settings.tsx: native settings already support description, homepage, Issues/Wiki flags, merge methods, and deleting merged head branches. Preserve permissions, drafts, conflicts, and uncertain-save confirmation.
- apps/desktop/src/screens/actions/run.tsx and runs.tsx: native run/job/log and workflow-list functionality exists; reuse it.
Evidence is source inspection, not a live authenticated app usability test. No running local app was found. No product files have been changed.

## Alternatives considered
1. Selected: entity page shell → Pull requests tab → scoped Inbox list + PR detail. One shared Inbox interaction, with both entity navigation and PR context retained.
2. Keep each dashboard as the left source pane. Preserves its content, but repeats the differing view patterns Yi wants to remove.
3. Keep separate pages and improve breadcrumbs. Smallest change, but does not satisfy the request to retain visible context.

## Navigation contract
The application sidebar, entity header, and entity section tabs retain their position when a detail opens. Organization/team section tabs are Overview, Repositories, and Pull requests. Repository tabs are Code, Pull requests, Actions, and Settings. Global Inbox uses the same split component without inventing an entity header. Existing bookmarks and default landing destinations continue to work.
The shared Inbox owns its filters, sort, selected row, pagination, and scroll, keyed by account and scope. Organization/team landing views keep Overview as the default. Choosing Pull requests changes only the entity tab panel to its scoped Inbox. Repository Pull requests embeds that same component. Opening a PR from Recently Synced Open Pull Requests switches the same entity page to Pull requests and selects that PR, keeping its header and tab bar. Existing Code URLs still open Code. Opening a PR adds a detail selection to that source route rather than replacing the source. Inside the selected Pull requests tab panel, show a compact source pane on wide layouts (approximately 300–360px) and the remaining width for detail; closing expands the same scoped Inbox. Closing a PR stays in the Pull requests tab; the existing Overview/Code tabs return to those sections. Browser Back reverses the original overview-to-PR navigation. Switching parent tabs preserves the scoped Inbox filters, scroll, and PR selection for returning during the session; it does not leave the Inbox visible in unrelated sections. Do not mount a second hidden copy of the source or refetch it just because a detail opened.
At less than 1000px available Pull requests tab-panel width, show one inner pane at a time. The entity header and parent tabs remain visible; their row can scroll horizontally if needed. Keep source state mounted and provide an explicit Back to [source] control. Restore scroll and focus to the originating item, or the source heading if the item disappeared. No horizontal page scrolling is acceptable.
Keep scope in the entity route params and derive it for the embedded Inbox; do not allow a conflicting independent scope value. Extend entity search validation with tab=pulls plus selected PR identity, pullTab, and optional run/job identity. Parent tab and inner PR tab must be separate fields. Legacy /g links resolve to their entity Pull requests tab; the global Inbox route uses the same component directly. Do not keep a second PR-list implementation. Push history for changing parent sections, opening/changing PR, or opening a run; replace for inner PR-tab/job changes. Back closes the run first, then the PR; Forward restores both. Close buttons target the known parent URL and do not blindly navigate outside the app. Keep all identities account-scoped; clear retained state on account change/sign-out.
Existing standalone PR/run URLs remain valid through thin route adapters sharing the same content components. Direct PR links resolve to the repository page with Pull requests selected and the PR open in its embedded Inbox, including when the PR is not in its current list. Direct run links use that repository's Actions source. Reload restores URL-selected content; session-only scroll/filter retention is not promised across a cold restart. Never invent an organization/team origin for a direct link.
Do not build a generic window manager or an unlimited stack of panes. Support a source, one PR detail, and one run dialog. Navigate between organizations/teams/repositories normally within the workspace; Back restores the previous source.

## Scoped Inbox data and state
Treat organization/team/repository as a separate filter from the existing Involving me / All scope toggle. Global Inbox retains its current default; explicit organization/team/repository scopes default to All within that scope, with Involving me available. Scope is visible in the entity header and cannot be cleared within an entity page; the global Inbox sidebar entry opens the unscoped view. Preserve Pin, Snooze, Settle, failure filters, keyboard interaction, and saved ordering; preferences remain account + PR based so the same PR does not acquire conflicting state across scopes.
Use existing group membership/sync for organization and team scopes, and exact owner/repository matching for repository scope. Do not infer a team from its organization or PR author. Current groupSearchQueries in packages/core/src/sync/groups.ts:127 uses org search for organizations and the team repository catalog for teams; preserve that meaning (open PRs in team repositories, not only team review requests). Filter raw group copies by exact groupId before deduplication so a copy from another group cannot erase membership. Preserve involvement membership from the full raw set when intersecting with Involving me. Repository matching uses exact normalized owner/name. Add regression cases for duplicate copies and stable preferences across scopes. Watch/refresh the selected source, not only the personal me group. Preserve the current coverage labels: recently synced is not an exhaustive GitHub inventory. Repository open PR pagination must keep its existing API coverage when moved into shared Inbox rows; do not silently narrow it to personally involved or previously cached PRs. Adapt data into one view model without duplicating UI or overwriting richer cached records with summary-only REST responses.
Keep order reconciliation over the full account set, then apply scope to display. Filtering must not delete hidden PRs or renumber their preferences. Define drag/drop against global neighbors or disable reordering while scoped with a clear explanation; initial proposal disables scoped drag/drop, retaining Pin/Snooze/Settle. Preserve filter and scroll per account/scope during this session; reset safely on account changes. A selected PR removed by a filter remains visible in detail with an explanation rather than selecting a different PR automatically.

## PR layout and checks
Use the actual PR pane width, not the window width, to choose the layout. Retain the existing 1152px threshold initially. Move the responsive measurement/container to include the PR header and content, so tabs and checks share one condition.
Wide PR: Conversation and Files changed tabs; checks remain available in the right rail for both views. Hide the Checks tab only when that rail is visible. Keep check counts/status in the rail. A wide checks deep link or shortcut 3 goes to Conversation and focuses the checks rail. If resizing while Checks is selected, normalize to Conversation using replace, never leave an invisible selected tab. Narrow PR: Conversation, Files changed, Checks tabs, with no duplicate rail. Preserve Files selection when resizing.
A GitHub Actions check opens a titled run dialog with jobs and logs inside it; the PR and source remain underneath. Reuse run refresh/actions/approval behavior and its permission checks. External checks continue to open their provider with a clearly external action. Escape closes only the top dialog, restores trigger focus, and must not also execute the PR's Escape shortcut. Use the existing accessible dialog component with focus trapping, labelled Close, internal scrolling, and fullscreen presentation on small windows. Preserve PR drafts and scroll while the dialog is open.

## Repository workspace
One repository header: owner/name, description, visibility/archive status, and Open on GitHub. One obvious navigation row: Code | Pull requests | Actions | Settings. Preserve native behavior of all four sections. Settings remains discoverable, with read-only presentation when the user lacks admin access; unavailable data and permission denial must remain honest.
Code uses approximately 28% width for a file navigator and 72% for content, with a practical navigator cap near 320px. README is the default right pane. Selecting a file shows its contents there while the navigator stays visible. Selecting a directory shows its listing on the right and expands that directory in the left navigator; breadcrumb/parent controls and selected state make the location explicit. Load expanded directories on demand, never crawl the whole repository. Root/README control restores the default preview.
Retain branch and path in the URL. On direct file links load its ancestor listings so the navigator can locate it. Branch changes reset to root, clear incompatible selection, and reject stale responses. Reuse getContents/getReadme, file limits, binary/unsupported fallbacks, and sanitized README rendering. Keep load/error/retry states local to the failing pane.
Below 800px repository content width, replace the fixed navigator with a Files drawer and use the full main pane for content. Closing it restores focus. PR source panes and repository navigator panes are not piled up indefinitely: opening a PR shows the repository-scoped Inbox on the left instead of stacking a file navigator beside it; returning to Code restores branch/path.
Pull requests is the shared Inbox filtered to this repository and opens PRs in the same split pattern. Actions uses the existing workflows/run filters and opens run details in the same dialog pattern. Settings uses the existing form; leaving a dirty form requires app-controlled Save/Discard/Stay handling, with no silent draft loss.
Richer information in this slice means surfacing already available metadata and native capabilities. Add a More on GitHub menu for Issues, Releases, Discussions, Projects, Security, Insights, and remaining settings, clearly labelled as external destinations; do not claim availability or display counts that have not been loaded. Native implementations of those additional GitHub areas require a separately scoped plan. Do not expand repository mutation permissions or add destructive settings.
